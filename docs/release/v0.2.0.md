# @tanstack-start/theme v0.2.0

Theme hydration stabilization release.

This release clarifies and stabilizes the split between pre-hydration DOM setup and React theme state. The main goal is to make `useTheme()` see the value passed to `ThemeProvider` on the first render, instead of briefly observing a module default.

## Highlights

- Added a first-render-safe `ThemeProvider` model backed by React Context.
- `useTheme()` now reads the provider context directly when available.
- `ThemeProvider` initializes its state from the `theme` prop during the first render.
- `ThemeInitScript` remains responsible only for pre-hydration DOM setup:
  - `<html>` classes
  - `data-theme`
  - `data-resolved-theme`
  - `color-scheme`
- Removed the need to initialize React theme state through route `beforeLoad`, router `hydrate`, or `useEffect`.
- Clarified `systemPreference` behavior:
  - `theme` is the selected user preference, such as `system`
  - `resolvedTheme` is the concrete visual theme, such as `light` or `dark`

## Migration notes

Recommended app setup:

```tsx
<ThemeInitScript theme={context.theme} />

<ThemeProvider theme={context.theme}>{children}</ThemeProvider>
```

Place `ThemeInitScript` in `<head>` when possible so the DOM theme is applied before React hydrates.

`ThemeInitScript` does not initialize React state. React state comes from `ThemeProvider`.

Apps that previously called `hydrateTheme(context.theme)` in route `beforeLoad` or router `hydrate` for initial state can remove that call when using `ThemeProvider`.

## API notes

`hydrateTheme(theme)` remains available for advanced/manual DOM synchronization, but normal app setup should prefer:

1. Server/router context reads the persisted preference.
2. `ThemeInitScript` applies DOM classes before hydration.
3. `ThemeProvider` initializes React Context state from the same preference.
4. UI controls call `useTheme()`.
